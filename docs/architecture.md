# Архитектура SAQ QURYLYS

## Слои

- `public/` — одностраничный интерфейс на обычном HTML, CSS и JavaScript. Маршруты клиента соответствуют обзору, реестру, карточкам ЖК, объявлениям, сигналам и истории.
- `src/server.mjs` — HTTP API на `node:http`, проверка JSON-запросов, обслуживание статических файлов и инициализация SQLite.
- `src/*-service.mjs` — операции над объявлениями, объектами, факторами, сигналами и аудитом.
- `src/risk-engine.mjs` — детерминированный расчёт баллов и зон, изолированный от AI-провайдера.
- `src/object-conditions.mjs` — неизменяемые решения МИО по дополнительным условиям green, источник/дата, привязка к контексту объекта, записанные политика/окно актуальности и история. Версия зон сохраняется отдельно от версии весов; отсутствие подходящей проверки оставляет объект yellow без добавления баллов.
- `src/complaint-service.mjs` — ручной приём обращений, неизменяемое тело/цепочка решений, согласованная проекция verified и управление связанным R4. Сигнал замораживает материал и журнал; `public/complaints-ui.js` показывает процесс во вкладке ЖК. Это не интеграция с внешним гражданским сервисом.
- `red_monitoring_state` в SQLite — последнее наблюдавшееся состояние red, эпизод, отпечаток подтверждённых факторов и граница существовавших карточек. Новый вход в red и изменение подтверждённых доказательств атомарно фиксируют карточку/внутреннее уведомление; неизменённая оценка не создаёт дубли при перезапуске.
- `src/ai-analyzer.mjs` — локальный rule-based extractor и необязательный адаптер OpenAI Responses API с JSON Schema.
- `src/payment-model.mjs`, `models/payment-linear-v1.json` — локальный обученный классификатор предложений платежа; веса и синтетическая обучающая выборка включены в проект. Это режим по умолчанию `local-ml`; отдельный режим `rule-based` сохраняется.
- `src/signal-export.mjs` — самостоятельная печатная HTML-карточка с полными снимками текстов; `/api/signals/:id/export` открывает её, `?download=1` задаёт скачивание.
- `src/signal-inbox.mjs` — краткие SQL-проекции без base64 для списков/обзора, ролевые границы до подсчётов, состояния сроков и составные курсоры. `public/signal-inbox-ui.js` — фильтры, счётчики, сроки и страницы. Полные снимки читаются только из отдельной карточки/экспорта.
- `src/collection-service.mjs`, `src/source-adapters.mjs`, `src/public-http.mjs` — настроенные источники HTML/JSON, сохраняемая очередь с арендой и повторными попытками, проверка сетевых адресов и версионируемые публикации.
- `src/access-service.mjs` — пользователи, scrypt, сессии, лимиты входа, роли, отзыв доступа и восстановление пароля.
- `src/db.mjs:inTransaction` — после BEGIN повторно проверяет идентичность/версию/роль/активность текущего сотрудника и его HTTP-сеанс. Обработка конкурентных версий настроек, проверки фактора и перехода сигнала читает состояние под блокировкой. Внутренние пересчёты выполняются как System; login/logout имеют отдельные ограниченные потоки идентичности.
- `src/http-policy.mjs` — фиксированный публичный HTTPS origin, проверка Host/Origin, доверенный прокси и адрес клиента, cookies и защитные заголовки. Локальная health-проверка проходит до загрузки сеанса.
- `src/backup-service.mjs`, `scripts/backup.mjs` — согласованные копии SQLite, хеши/проверка внешних ключей, миграция копии и восстановление в новый файл с отключением старого доступа и фоновых задач.
- `src/business-calendar.mjs` — неизменяемые версии календаря, исключения, рабочие переносы и расчёт срока с проверкой покрытия.
- `src/dataset-service.mjs` — разделение демонстрационной и рабочей баз, требования к администратору и запрет смешивания режимов.
- `data/saq-qurylys.sqlite` — локальная база; записи демо помечены `is_demo=1`.

Приложение не требует npm-пакетов и сборщика. Пока в демонстрационной базе нет пользователей, действует явно обозначенный локальный доступ с актором `Demo Analyst`. После создания администратора API требует сессию и проверяет роли. Рабочий режим требует заранее созданного действующего администратора; это остаётся локальным развёртыванием без подтверждения промышленной инфраструктуры и требований размещения данных.

## Поток публикации

1. Аналитик сохраняет платформу, дату, текст и при необходимости URL, аккаунт, телефон и заметку.
   Альтернативно настроенный источник получает публикации автоматически: архив, происхождение, публикация, аудит и задачи анализа фиксируются одной транзакцией. Анализ выполняется отдельно; неизвестная дата публикации остаётся неизвестной в происхождении и экспорте.
2. Анализ извлекает структурированные поля и точные цитаты из введённого текста. Каждая цитата проверяется как подстрока источника.
3. Entity matcher ранжирует варианты ЖК по названию, адресу, застройщику и контактам. Предложенный ID сохраняется отдельно от подтверждённого `complex_id`.
4. Только действие аналитика связывает объявление с объектом. После этого допустимые R2/R3 создаются как `AI_HYPOTHESIS` и дают 0 баллов.
5. Аналитик подтверждает либо отклоняет каждый фактор. Перед подтверждением проверяется, что фрагмент есть в тексте источника.
6. Пересчитанный балл, история и аудит обновляются. Каждый подтверждённый код начисляется один раз, независимо от числа источников.
7. Создание сигнала фиксирует факторный снимок и `context_snapshot_json`: реквизиты объекта, правовой источник, версии исходных текстов публикаций. SQLite-триггер запрещает менять снимки, автора, время создания и связанный объект. Новые сведения отражаются только в текущей карточке ЖК и новых сигналах.

При открытии старой базы выполняется добавление nullable-поля снимка контекста. Отсутствующий исторический контекст не реконструируется из текущих публикаций; интерфейс показывает предупреждение. Сама запись сигнала сохраняется.

## Схема данных

| Таблица | Назначение |
| --- | --- |
| `complexes` | Карточка объекта, заявленная и проверенная готовность, правовой статус |
| `complex_contacts` | Телефоны и аккаунты, которые помогают сопоставить источник |

| `risk_factors` | Код, вес, доказательство, источник и статус фактора |

| `signals` | Неизменяемый снимок риска и этап проверки |
| `risk_history`, `audit_logs` | Изменение оценки и журнал действий |
| `users`, `sessions`, `auth_attempts` | Учётные записи, хешированные токены сеансов и сохраняемые лимиты попыток |

| `source_archives`, `collected_publications` | Неизменяемые исходные ответы и происхождение версий публикаций |

## API

Управление источниками и очередью реализовано в `public/collection-ui.js`/`public/collection.css`, разделы `/settings?section=sources` и `/settings?section=jobs`. Очередь поддерживает курсор и фильтры, включая анализ публикаций выбранного источника. Подробности задачи связывают результат с публикациями, архивом и ограниченной историей событий. Архив успешной задачи скачивает только ADMIN; доступ к архиву публикации отдельно проверяется по существующей области материала. Коды ошибок добавлены без переписывания старых задач; неизвестные сообщения провайдера не попадают в публичную диагностику.

Календарь представлен в `public/calendar-ui.js`/`public/calendar.css`, раздел `/settings?section=calendar`. Сервер использует общую проверку определения для предпросмотра и публикации. Предпросмотр возвращает отпечаток нормализованного черновика без записи; интерфейс связывает результат также с датой проверки и действующей версией. Публикация проверяет `expectedVersion` и, если передан, `expectedDraftSha256`. История выдаётся страницами с курсором по времени и порядку создания, без ограничения доступности первыми 100 версиями.

Управление доступом отображается через `public/access-ui.js` и `public/access.css`. Принудительная смена временного пароля проверяется по `/api/auth/session` до запроса bootstrap. Обычная смена доступна на `/account`, административные операции — на `/settings?section=users`; каждая изменяющая операция дополнительно проверяется сервером и связывается с версией записи. Пароли не сохраняются в browser storage; язык и незаписанные поля при переводе восстанавливаются только в текущей странице.

Фотоотчёты строительства, их неизменяемые решения и история готовности хранятся отдельно в `construction_observations`, `construction_reviews`, `readiness_history`. Паспорт ссылается на применённый отчёт; `readiness_revision` связывает R5 с конкретными исходными сведениями. Новые снимки сигналов версии 2 включают применённую фотографию и ограниченную историю с явными количествами. Старые снимки не дополняются текущими материалами. [Контракт фотофиксации](backend-construction.md).

Интерфейс фотоотчётов выделен в `public/construction-ui.js` и `public/construction.css`: вкладка ЖК «Ход строительства», приём файла, проверка, исправления, страницы истории и отображение сохранённого фото в сигнале. `public/app.js` получает страницы и выбранный отчёт через API; при конфликте обновляет версию паспорта с сохранением решения. Доступ к формам определяется ролью, а сервер независимо проверяет полномочия и назначение объекта.

`GET /api/bootstrap`, `/api/complexes`, `/api/complexes/:id`, `/api/ads`, `/api/ads/:id`, `/api/signals`, `/api/signals/:id`, `/api/history` читают данные. Изменяющие маршруты — `POST /api/ads`, `POST /api/ads/:id/analyze`, `POST /api/ads/:id/match`, `POST /api/complexes/:id/factors`, `POST /api/complexes/:id/legal-basis`, `POST /api/factors/:id/review`, `POST /api/signals` и `PATCH /api/signals/:id/status`.

Изменения материалов и операций доступа фиксируют аудит. API принимает JSON до 1 МБ, отклоняет неверный тип тела и изменяющие запросы с другого Origin. Повторное подтверждение той же связи идемпотентно; перевод к другому ЖК блокируется, чтобы не оставить доказательства у прежнего объекта. Проверка фактора поддерживает ожидаемый статус для предотвращения перезаписи устаревшего решения. Административные изменения учётных записей и календарей используют проверку версии. Назначение сохраняет календарь и срок; изменение зафиксированных реквизитов назначения и результата запрещают триггеры SQLite. Сессия проверяется повторно после получения тела запроса, а асинхронные операции с паролями проверяют актуальность доступа перед фиксацией.
