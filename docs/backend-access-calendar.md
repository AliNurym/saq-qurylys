# Доступ сотрудников и сроки рассмотрения

Бэкенд поддерживает создание, отключение и восстановление доступа сотрудника, смену его роли, отзыв сеансов и восстановление пароля администратором. Операции сохраняют аудит и работают с проверкой версии записи. Удаления учётных записей нет: авторы исторических решений и журнал сохраняют свои идентификаторы.

## Управление учётными записями

### Работа через интерфейс

Администратор открывает «Настройки → Сотрудники». Раздел отделён от правил риска: слева список сотрудников с состоянием доступа, справа выбранная запись и форма действия. Доступны изменение роли/активности, завершение всех сеансов и выдача нового временного пароля. Каждое действие требует причины. Последний действующий ADMIN помечен явно; интерфейс блокирует его отключение/смену роли, сервер независимо запрещает эти операции.

Если запись уже изменилась, операция возвращает 409 и показывает кнопку «Обновить список». Обновление сбрасывает незаписанное действие и поля пароля: проверьте свежую запись и выберите действие заново. Изменение собственного доступа либо отзыв собственных сеансов приводит к форме входа. При переключении операции поле временного пароля очищается; при смене RU/KZ выбранная операция и введённые значения остаются в памяти страницы. Пароли не записываются в URL или browser storage.

«Добавить сотрудника» создаёт аккаунт с первоначальным временным паролем и `mustChangePassword=true`. Первый администратор создаётся без этого признака: первоначальный пароль задаёт сам оператор настройки. API принимает необязательное логическое `mustChangePassword` при создании; по умолчанию оно `false` для совместимости с командой локального создания и существующими клиентами. Неверный тип отклоняется до записи. Признак включается в безопасные метаданные аудита, сами пароли не включаются.

При входе с обязательной сменой пароля интерфейс показывает отдельную форму до запроса bootstrap/материалов. Сотрудник вводит полученный временный пароль и дважды новый личный. Доступен выход и RU/KZ; обычная навигация и материалы отсутствуют. Сервер продолжает независимо ограничивать операции такого аккаунта. После успешной смены требуется вход с новым паролем.

Любой вошедший сотрудник открывает «Учётная запись» для обычной смены своего пароля. Она также завершает все его сеансы. Сравнение двух новых значений выполняется в браузере; проверка текущего пароля, ограничение попыток, отличие нового пароля и отзыв сеансов выполняются сервером.

Локальная инициализация первой учётной записи через браузер, SSO/MFA и восстановление по почте — разные возможности. Новые формы не добавляют корпоративную идентификацию и не подтверждают промышленное размещение. Начальная настройка через CLI и защита от удалённого создания первого администратора сохранены.

### Контракт API

Администратор получает список через `GET /api/admin/users`. В ответе есть `id`, `username`, `role`, `enabled`, `mustChangePassword`, `createdAt`, `updatedAt`. Хеши паролей, соль и идентификаторы сеансов не возвращаются.

Отключение или смена роли: `PATCH /api/admin/users/:id`.

```json
{
  "enabled": false,
  "reason": "Сотрудник больше не работает с материалами",
  "expectedUpdatedAt": "значение updatedAt из последнего GET"
}
```

Для смены роли используется `role`: `MIO`, `GASK`, `LAW_ENFORCEMENT` или `ADMIN`. При изменении роли или активности завершаются все сеансы сотрудника. Повторное включение не восстанавливает старые cookies: нужен новый вход. Последнего действующего администратора нельзя отключить или понизить в роли. Даже если все аккаунты отключены вне приложения, система не переходит обратно к анонимному демодоступу.

Явный отзыв всех сеансов: `POST /api/admin/users/:id/revoke-sessions`, тело содержит `reason` и `expectedUpdatedAt`. Причина — 5–1000 символов. Устаревшая версия возвращает 409, запрещённая роль — 403, завершённый сеанс — 401.

Сброс пароля: `POST /api/admin/users/:id/password`.

```json
{
  "newPassword": "временный пароль от 12 до 200 символов",
  "reason": "Восстановление доступа по обращению сотрудника",
  "expectedUpdatedAt": "значение updatedAt из последнего GET"
}
```

Старые сеансы отзываются. Новый пароль должен отличаться от прежнего. При следующем входе возвращается `mustChangePassword=true`: материалы и административные операции недоступны до смены пароля. Доступны проверка собственного сеанса, выход и `POST /api/auth/password`:

```json
{
  "currentPassword": "полученный временный пароль",
  "newPassword": "новый личный пароль сотрудника"
}
```

После успешной смены отзываются все сеансы, cookie текущего входа очищается, ответ содержит `reauthenticate=true`. Нужно войти с новым паролем. Пароли не попадают в аудит или ответы API.

Проверка scrypt при входе и смене пароля выполняется асинхронно. Лимиты попыток находятся в SQLite и сохраняются после перезапуска: до 10 попыток на сочетание имени и сетевого адреса за 10 минут, до 100 запросов входа с одного адреса за тот же период. Успешный вход очищает счётчик сочетания, общий адресный счётчик сохраняется. Для смены пароля применяются отдельные такие же счётчики. Ключи адресов в таблице хешированы. Превышение возвращает 429 и `Retry-After`; прокси-заголовки не используются для определения адреса клиента.

Перед записью после получения тела запроса права проверяются повторно: медленный запрос не может сохранить ранее отозванные полномочия. Вход и асинхронные операции с паролями также проверяют актуальность аккаунта перед завершением. Аудит операций с доступом и отзыв сеансов находятся в одной транзакции.

Первого администратора в деморежиме можно создать только через локальное соединение или команду `scripts/create-user.mjs`. Команда также требует первым создать ADMIN и сохраняет аудит. В рабочем режиме администратор создаётся до запуска сервера. Самостоятельное восстановление по почте, корпоративный SSO и MFA в этот этап не входят.

## Календарь рабочих дней

Администратор читает текущий календарь через `GET /api/admin/calendar` и публикует новую версию через `PUT /api/admin/calendar`:

```json
{
  "expectedVersion": "версия из GET",
  "coverage": { "from": "2026-10-01", "to": "2026-12-31" },
  "nonWorkingDates": ["2026-10-25", "2026-10-26", "2026-12-16"],
  "workingDates": [],
  "source": "Документ, ссылка и пояснение проверки календаря",
  "sourceDate": "2026-10-19"
}
```

`sourceDate` обозначает дату документа или выполненной сверки; её смысл нужно указать в `source`. Выходными по умолчанию считаются суббота и воскресенье. `nonWorkingDates` исключает дополнительные даты, `workingDates` учитывает рабочие переносы, в том числе на субботу. Дубли, несуществующие даты, конфликтующие исключения и даты вне периода отклоняются. Публикация сохраняет отдельную неизменяемую версию, автора, время, источник и SHA-256 определения. Одновременные изменения проверяются через `expectedVersion`.

Проверка срока по действующему календарю без назначения: `POST /api/admin/calendar/preview` с `{ "startDate": "2026-10-19", "days": 5 }`; ответ помечен `mode: ACTIVE`.

Для проверки неопубликованного определения передайте `draft` с полями `source`, `sourceDate`, `coverage`, `nonWorkingDates`, `workingDates`, а также `startDate`, `days` и `expectedVersion` действующего календаря. Ответ `mode: DRAFT` содержит срок, `draftSha256` нормализованного определения и сравнение с действующими настройками. Если действующий календарь не покрывает срок, сравнение содержит объяснение ошибки; корректный расширенный черновик при этом может пройти проверку. Предпросмотр не записывает версию, аудит публикации или настройку.

При публикации можно передать `expectedDraftSha256` из предпросмотра. Сервер отклоняет изменённое определение с 409; проверка `expectedVersion` также обязательна. Отпечаток черновика не равен SHA-256 сохранённой версии: окончательный снимок дополнительно включает идентификатор, автора и время. Для совместимости прямой API допускает публикацию без `expectedDraftSha256`; интерфейс требует успешной проверки текущего черновика перед активацией кнопки публикации.

История: `GET /api/admin/calendar/versions?limit=20&before=VERSION`, `limit` 1–100. Ответ содержит `items`, `total`, `nextCursor`. Курсор учитывает порядок создания, включая одинаковые временные метки; старые версии доступны после первых 100 записей. Полный снимок: `GET /api/admin/calendar/versions/:version`.

### Календарь в интерфейсе

Администратор открывает «Настройки → Рабочие дни». Видно, опубликован календарь или работает резервный режим. Для новой версии задаются источник/дата сверки, период, дополнительные нерабочие дни и рабочие переносы. В каждом списке — одна дата `YYYY-MM-DD` в строке. Праздники не подставляются автоматически; пустой список означает отсутствие исключений.

«Проверить расчёт» выполняет серверный расчёт пяти дней после выбранной даты назначения и сравнивает его с действующими правилами. После изменения полей результат сбрасывается; публикация снова недоступна до проверки. RU/KZ сохраняет поля и подходящий результат. Конфликт версии предлагает обновить настройки; обновление загружает актуальные данные и сбрасывает незаписанный черновик.

История показывает неизменяемые определения, автора, источник и хеш. Просмотр старой версии не активирует её. «Скопировать в новый черновик» переносит только редактируемые поля; перед публикацией новой версии необходимо повторить проверку. Просмотр истории доступен страницами. В карточке назначенного сигнала отображаются версия и источник, зафиксированные при назначении; текущий календарь вместо них не подставляется.

Предпросмотр одной даты проверяет механизм расчёта и покрытие этого срока, но не доказывает полноту праздников за весь период. Подлинность источника, полноту исключений и соответствие официальным документам подтверждает оператор. Настройка календаря не меняет длительность срока из ТЗ: интерфейс использует пять рабочих дней.

Для сигнала отсчёт пяти рабочих дней начинается после дня назначения. Календарь должен покрывать и дату назначения, и весь расчёт до срока включительно. При недостаточном покрытии назначение возвращает 409 без изменения сигнала или записи об одобрении. Версия и определение календаря фиксируются при назначении; последующие настройки не сдвигают уже сохранённые сроки. Исторические назначения без снимка календаря не получают выдуманную историю. Получатель вносит результат один раз. Изменение зафиксированных полей назначения или результата дополнительно блокируют триггеры SQLite.

До первой публикации работает обозначенный резервный режим: суббота, воскресенье и `SAQ_NON_WORKING_DATES`. Это не подтверждённый официальный календарь. Печатный экспорт показывает, какой режим и какая версия использованы. Публикация календаря оператором также не означает автоматической юридической проверки исходных сведений.

Подготовлен [шаблон для IV квартала 2026 года](examples/business-calendar-kz-2026-q4.json), сверенный 19 октября с [официальным производственным календарём](https://www.gov.kz/article/16887?lang=ru): он содержит День Республики, перенос выходного на 26 октября и 16 декабря. Шаблон рассчитан на пятидневную неделю и ограничен указанным кварталом. Для публикации нужно добавить текущий `expectedVersion`; он автоматически в базу не загружается. Для назначения, срок которого выходит в январь 2027 года, понадобится календарь следующего периода.

## Проверка

Проверены миграция старых аккаунтов без изменения паролей, отзыв всех сеансов, восстановление и смена роли, защита последнего администратора, конфликт версий, атомарность аудита, смена временного пароля, отказ операций при отзыве доступа во время запроса и сохранение лимитов после повторного открытия SQLite. Для календаря проверены праздничные дни, рабочие выходные, високосный день, переход года, границы покрытия, неизменяемость версий, сохранность старых назначений, HTTP-права и печатный экспорт. Проверки используют изолированные базы и временные HTTP-порты.
