# Обращения граждан: ручная регистрация и проверка

Карточка ЖК → «Обращения» — рабочий журнал МИО. Он хранит поступивший материал и последовательность решений. Внешняя система обращений граждан не подключена; запись не подтверждает реальную регистрацию в государственном сервисе.

## Порядок работы

1. МИО выбирает индивидуальное/коллективное обращение, указывает дату поступления, источник, содержание и регистрационный номер при наличии. Материал получает PENDING, **без баллов**.
2. МИО проверяет сведения и сохраняет CONFIRMED либо REJECTED с отдельными датой, источником, проверенным содержанием и основанием решения. Подтверждение сведений не означает установленное нарушение закона.
3. Для подтверждённого материала можно зафиксировать RESOLVED по источнику результата либо отозвать подтверждение (REJECTED). Это новое решение, прежнее остаётся в истории.
4. После отклонения или разрешения можно снова подтвердить материал по новой проверке. Цепочка решений и авторы сохраняются.

Поступление/проверка не могут иметь будущую или несуществующую дату; проверка не предшествует поступлению. Дата поступления — утверждение оператора; фактическое время регистрации сохраняется отдельно сервером. Время создания решения также задаётся сервером. Исторические даты не обрезаются произвольной границей 2010 года.

Исходные тип/ЖК/содержание/источник/время регистрации и журнал приёма неизменяемы. Ошибочно зарегистрированный материал не удаляется и не переносится между ЖК: его нужно отклонить с объяснением и зарегистрировать правильный материал отдельно. Копирование абсолютно одинаковых нормализованных полей идемпотентно и возвращает прежнюю карточку. Это не автоматическое распознавание всех дублей одного обращения по изменённому тексту.

## Влияние на риск

- R4 создаётся только для **COLLECTIVE + CONFIRMED**. Индивидуальное или непроверенное обращение этот коллективный фактор не создаёт.
- Несколько подтверждённых коллективных обращений дают вес R4 один раз по общей формуле, по умолчанию +15.
- Разрешение/отзыв переводит связанный с данным обращением R4 в REJECTED. Подтверждённое другое обращение продолжает давать R4. Повторная проверка может снова включить тот же связанный фактор.
- Другие ручные/исторические R4 автоматически не снимаются: это отдельные доказательства, а не дубли по умолчанию.
- Связанный фактор нельзя изменить через общий `/api/factors/:id/review`: сервер возвращает 409 и направляет в журнал обращения. Решение, проекция проверки, фактор, история риска и аудит сохраняются одной транзакцией.

В базовой таблице `verified=true` означает подтверждённость сведений, а не наличие незавершённого дела: RESOLVED остаётся проверенным материалом. Для текущего состояния используется `status`.

Поступление нового материала и новые решения меняют контекст проверки условий зелёной зоны. Снятие R4 **само по себе не возвращает green**: нужна подходящая актуальная проверка МИО по остальным условиям. Значимость индивидуальных жалоб не устанавливается автоматически моделью.

## Доступ, интерфейс и история

Регистрация и решения доступны только МИО после авторизации. ADMIN читает доступные материалы, но не вносит решение за МИО. ГАСК/правоохранительный орган читает обращения назначенного ему ЖК по существующей границе доступа; чужой объект недоступен.

Есть фильтры вида/состояния, страницы списка и выбранная карточка с полным журналом решений. Поля решения привязаны к идентификатору обращения. Конфликт последнего решения — 409 без перезаписи; черновик сохраняется, после явного обновления недоступный теперь вариант решения нужно выбрать заново. Просмотр страниц списка сохраняет черновик приёма/проверки и выбранное обращение. Поддерживаются RU/KZ.

Исторические записи старой таблицы показываются отдельно как LEGACY_CONFIRMED/LEGACY_UNVERIFIED. Автор/дата поступления/история решений не выдумываются. Через новый процесс они не редактируются; новая запись не снимает старый независимый фактор автоматически.

## HTTP

- `GET /api/complexes/:id/complaints?status=&type=&limit=5&before=` — список с курсором, количеством и фильтрами. Лимит 1–100; порядок регистрации, новый материал первым. Курсор привязан к ЖК и фильтрам.
- `POST /api/complexes/:id/complaints` — `type`, `receivedDate`, `source`, `summary`, необязательный `registrationNumber`. Новая запись — 201, точный повтор — 200 с `created=false`.
- `GET /api/complexes/:id/complaints/:complaintId` — исходный материал и журнал решений.
- `POST /api/complexes/:id/complaints/:complaintId/review` — `status`, `checkedDate`, `source`, `evidenceText`, `reason`, обязательный `expectedReviewId` (null для первого решения). Недоступный переход или устаревшая версия — 409.

Доступ проверяется на сервере и повторно после чтения тела. Входные строки/даты/состояния валидируются до записи. SQL-триггеры запрещают изменение приёма/журнала и тела зарегистрированного материала; поле verified следует последнему решению. Код не удостоверяет подлинность документа и не делает внешних отправок.

## Сигналы и восстановление

Новый сигнал сохраняет обращения, поступление и все решения на момент формирования. Интерфейс/автономный HTML показывают этот снимок; более позднее разрешение не меняет исторический балл, текст или решение. Ссылка фактора позволяет открыть текущее обращение отдельно. Старый сигнал без снимка не получает текущие обращения задним числом.

Резервная копия включает базовые обращения, неизменяемый приём/решения и связанные факторы. Восстановление проверяет сохранность исходных колонок. Сброс demo-базы с вручную зарегистрированными обращениями запрещён; для новой демонстрации нужна другая пустая база.

Проверки: 14 серверных сценариев, 7 интерфейсных и отдельное восстановление с журналом/фактором; браузерный процесс на изолированной SQLite working с синтетическими материалами. Реальная интеграция с системой обращений и достоверность реальных источников этим не подтверждаются.
